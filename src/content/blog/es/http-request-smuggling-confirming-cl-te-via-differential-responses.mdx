1. Con `Transfer-Encoding: chunked`, curl suele **eliminar o reescribir** `Content-Length`, y desaparece el conflicto de interpretación que necesitamos
2. Curl sigue "arreglando" la petición en lugar de enviar nuestros bytes tal cual

Así que dejamos el cliente HTTP de curl y enviamos HTTP/1.1 en bruto sobre TLS. Sigue siendo tooling simple, solo que no es Burp.

Vamos a reconstruir la misma idea sin Burp, paso a paso.

### Preparando la petición de smuggling CL.TE

Primero, contemos los bytes del **payload smuggled** (solo el body de nuestra petición; cada `\r\n` importa):

<CodeSnippet file="http-request-smuggling-confirming-cl-te-via-differential-responses/payload-len.py" />

> **Desglose del script**: \
`print(len(...))` = contar cuántos bytes tiene el body, para que `Content-Length` coincida exactamente \
`b"..."` = string de bytes, así `\r\n` son CRLF reales (no los caracteres `\` y `n`) \
`0` = chunk de tamaño cero: en encoding chunked significa "fin del body" para el back-end \
`\r\n\r\n` después de `0` = cerrar ese chunk vacío (línea de tamaño, luego línea en blanco) \
`GET /404 HTTP/1.1\r\n` = la request line smuggled que el back-end tratará como la siguiente petición \
`X-Ignore: X` = header dummy que absorbe el inicio de la siguiente petición real cuando se pegan \
`# 35` = la longitud que necesitamos en `Content-Length`

Coincide con `Content-Length: 35`.

**Así que en este ataque, cada servidor hará lo siguiente:**

1. **Front-end** recibe nuestra petición `POST /` y, usando `Content-Length: 35`, reenvía esos 35 bytes de body (nuestro payload smuggled) al back-end
2. **Back-end** usa encoding chunked (`Transfer-Encoding: chunked`), ve el chunk `0`, cree que la petición terminó y nos devuelve la respuesta de nuestro `POST /`
3. El back-end nunca lee `GET /404 HTTP/1.1\r\nX-Ignore: X`, así que esos bytes quedan sin leer en su buffer de recepción
4. La siguiente petición en esa conexión se pega al sobrante. Por ejemplo, si el próximo usuario (o nuestro segundo envío) empieza con `POST / HTTP/1.1...`, el back-end ve algo así:

<CodeSnippet file="http-request-smuggling-confirming-cl-te-via-differential-responses/leftover-glue.http" />

Por eso el back-end ejecuta nuestro `GET /404` smuggled, no lo que pidió el siguiente usuario. Su petición real (aquí `POST /`) solo se agrega a `X-Ignore`, que muy probablemente se ignora por ser un header desconocido. Así reciben **404 Not Found**, sin importar a qué endpoint querían llegar.

### Request smuggling con Python, luego disparar con curl

Primero usaremos sockets de Python para enviar la petición de smuggling una sola vez y dejar `GET /404` sin leer en el buffer del back-end. Después, en una conexión normal aparte, usaremos curl para pedir `/` como haría el siguiente usuario. Nuestro curl es una conexión de cliente nueva; el front-end igual puede reutilizar el mismo socket hacia el back-end, y así se aplican los bytes sobrantes. ## Mitigación

1. **Preferir HTTP/2 de extremo a extremo**: el smuggling CL.TE clásico necesita la ambigüedad de HTTP/1, así que HTTP/2 de extremo a extremo es seguro frente a *esta* variante. No es un salvoconducto contra todo desync; siguen existiendo otros estilos de request smuggling cuando HTTP/2 se degrada o se mezcla con HTTP/1 hacia el back-end
2. **Rechazar peticiones dudosas**: si vienen `Content-Length` y `Transfer-Encoding` juntos, rechazar y cerrar la conexión
3. **Hacer que ambos servidores coincidan**: el front-end debe limpiar peticiones; el back-end debe rechazar lo que siga siendo dudoso
4. **Cuidado con reutilizar conexiones**: apagar keep-alive hacia el back-end ayuda un poco, pero no es un arreglo completo
